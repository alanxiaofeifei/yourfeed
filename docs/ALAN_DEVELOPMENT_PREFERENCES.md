# Alan 的开发偏好与 AI Agent 工作规范

**版本：1.0**  
**核实日期：2026-11-14（Asia/Taipei）**  
**适用范围：个人软件项目、自动化项目，以及需要跨会话持续推进的开发工作。模型选择和上下文管理原则也适用于其他长任务。**

本文是一份可纳入项目的工作规范。标为“默认”的数值和流程是 Alan 的可调整偏好，不是行业统一标准。产品功能以当前工具版本、账号权限及官方文档为准。

## 0. 核心约定

**GitHub 是开发项目的权威记录。开发工具、模型、设备和运行环境可以更换，项目代码、确认过的需求、架构决策、计划、进度、验证证据及下一步应能从 GitHub 恢复。**

模型选择以可靠完成任务和总完成成本为目标，使用“工具／Agent 执行框架 + 模型版本 + 推理档位 + 可用能力”作为比较单位。ModelDial 是高权重外部参考，相关 Arena 榜单用于交叉检查，本项目的有效验证结果决定最终采用方案。

上下文是需要管理的工作资源。普通长任务以约 50% 的有效上下文占用作为主动检查与压缩触发点；先保存关键状态，在合适的阶段边界压缩。需要长上下文的任务可以例外，不以机械达标牺牲准确性。

本规范在既有权限、平台约束及项目要求内执行。已有明确授权的日常工作继续推进；涉及目标或授权范围的实质变化时，先把可完成的工作做成可审阅结果，再提出必要问题。

## 1. GitHub 为核心的持续开发

### 1.1 项目必须能回答的问题

一个没有旧聊天记录的新 Agent，应能从仓库及相关 GitHub 记录回答：

1. 项目解决什么问题？当前目标和范围是什么？
2. 目前实际采用什么技术栈、模块划分、接口和数据结构？
3. 已完成哪些工作？哪些只是计划或尚未验证？
4. 正在进行的工作位于哪个 Issue、PR 和分支？
5. 哪些重要决策已经确认？原因及约束是什么？
6. 如何安装、运行、验证和恢复开发环境？
7. 目前有什么阻塞、已知缺陷及有价值的失败尝试？
8. 下一步具体执行什么？如何判断完成？
9. 哪个版本已部署到哪个环境？有哪些实际验证证据？

记录应保存结论、依据、任务状态和必要操作信息。完整聊天、逐步思考和海量原始日志不是默认交付物。

### 1.2 最小文件集与职责

优先沿用现有项目结构。已有同等作用的文件，就在原位置维护，不为符合命名再建一份。

| 位置 | 职责 | 主要更新时机 |
| --- | --- | --- |
| `README.md` | 项目用途、快速启动、前提条件、文档入口 | 运行方式或项目能力发生变化 |
| `AGENTS.md` | Agent 的读取顺序、工作规则、常用命令和约束 | 工作方式发生变化 |
| `docs/PROJECT.md` | 当前技术栈与架构、重要约束、阶段计划和关键决策 | 设计、计划或实现发生实质变化 |
| `docs/STATUS.md` | 当前任务入口、分支／PR、验证状态、阻塞和下一步 | 形成检查点或任务状态变化 |
| GitHub Issues | 具体任务的需求、范围、验收条件与讨论 | 任务建立或要求发生变化 |
| GitHub PR 与运行记录 | 实际改动、审查、检查及关联版本 | 实现推进、审查或验证时 |

项目复杂后再按需要拆出：

- `docs/ARCHITECTURE.md`：当前架构、模块关系、接口和数据流。
- `docs/PLAN.md`：里程碑、顺序、依赖与范围。
- `docs/adr/`：重要架构决策记录，包含背景、选项、结论、取舍和替代关系。
- `docs/RUNBOOK.md`：部署、回滚、迁移与故障处理。
- `docs/MODEL_SELECTION.md`：当前适用的模型配置及验证依据。
- `.github/workflows/`：项目实际需要的自动检查或部署流程。

有 Issue 的任务，以对应 Issue 的当前任务记录为状态入口；没有 Issue 的小任务，以对应 PR 或明确指定的任务记录为入口。STATUS 保留索引和简短检查点，PLAN 描述阶段与依赖，Git 历史保存历次改动。避免把同一任务清单手工复制到多个文件。记录冲突时，根据更新时间、对应代码版本和验证证据核对，并修正过时记录。

文档里的“当前架构”应描述已经采用的实现。拟议设计必须明确标为“提议”或“计划”。发现文档与代码、检查结果或部署证据不一致时，应核对并修正文档。

### 1.3 每次开工的读取流程

1. 确认仓库及远程地址、当前分支、工作区改动、相关开放 PR，保护已有未提交工作。
2. 检查远程最新状态，使用不会覆盖现有工作的方式同步。不能盲目执行破坏性重置。
3. 按需读取：`AGENTS.md` → `README.md` → 当前状态 → 当前 Issue／PR → 本任务相关的架构、计划和代码。
4. 默认分支可能还没有进行中的改动；必须确认任务所在分支和 PR，不能只看主分支就判定“尚未开发”。
5. 明确本次目标、验收条件和最小下一步。已有任务继续原记录，避免重复开工单。
6. 只有当缺失信息确实影响执行或正确性时才询问；否则写明合理假设并推进。

不要默认全文读取整个仓库、全部历史或所有外部文档。先定位相关路径和符号，再读取必要内容。

### 1.4 工作过程与远程检查点

在已授权的仓库与流程范围内：

- 使用范围清楚的任务分支。代码、相关说明和验证结果应随实质进展保持一致。
- 在可恢复节点提交并推送，长任务可使用 Draft PR 暴露未完成进展。
- 用户新确认的需求和会影响后续的决定，应进入对应 Issue、项目文档或决策记录。
- 对有复用价值的失败尝试，记录“尝试了什么、证据是什么、排除了什么”；不要求保存每次无关失败。
- 阶段结束、暂停、切换环境、切换需要重新建立上下文的模型，以及可控的压缩操作前，更新当前检查点。
- 小改动可以用一次清楚的 commit／PR 留痕；复杂工作再使用独立 Issue、计划及审查。不要为每条聊天或每次工具调用创建记录。

GitHub 官方流程区分分支、commit、push、PR 和合并；推送后的改动才能从其他设备访问，Draft PR 可用于尚未完成的工作。[来源 S1]

**本地提交、远程推送、合并、部署和线上验证应分别报告。**

远程同步失败时，先保留本地提交或可恢复补丁，说明未同步的内容、位置和原因；恢复连接后再补推并核对。不能把“本地有文件”写成“其他环境已可接手”。

若网络或权限暂时不可用，可推进不依赖远程的独立工作；不能虚构 Issue、PR、commit URL 或同步结果。

### 1.5 环境复现与工具兼容

仓库应提供足够的环境信息：

- 运行时和包管理器版本、必要依赖及适用锁文件。
- 可直接使用的安装、启动、检查命令。
- `.env.example` 中的变量名和安全示例。
- 外部服务依赖、测试数据准备、数据库迁移要求。
- 必要时提供开发容器或等效配置；不要求每个小项目都容器化。

凭证由各环境的安全机制提供。仓库中只保留配置说明，不保存真实密钥、访问令牌、恢复代码或未脱敏的私人／业务数据。

`AGENTS.md` 是统一入口，但不同工具对指令文件的加载方式不同，Markdown 链接也不保证被指向的正文自动进入上下文。[来源 S2]

因此，切换工具时应：

1. 检查它实际支持的项目指令入口。
2. 必要时使用 `CLAUDE.md`、`.github/copilot-instructions.md` 或该工具当前支持的适配入口，明确要求读取项目的 `AGENTS.md`。
3. 将必须始终生效的核心规则保持在入口文件中；细节按任务显式读取。
4. 验证实际加载情况。适配入口只维护必要的工具差异，避免复制一整套容易漂移的项目规则。

“新环境可接手”的前提仍包括所需仓库权限、依赖和凭证。可迁移不等于任意机器都能零配置运行。

### 1.6 完成标准与验证证据

任务只有在满足约定验收条件后，才能标记为完成。交付至少说明：

- 改了什么、解决了什么问题。
- 实际执行了哪些相关检查，结果及对应代码版本。
- 未执行的必要检查，以及不能执行的原因。
- 已知剩余问题、限制或后续事项。
- Issue／PR／远程分支入口。
- 如涉及部署：目标环境、部署版本、运行记录及实际验证情况。

验证范围与改动风险匹配，并遵守项目已有门槛。低风险、可逆的小改动不强制新增测试；关键行为、权限、金额处理、迁移和并发改动需要有针对性的证据。各子任务检查通过后，仍需验证整合后的受影响路径。

GitHub 部署历史可以关联环境、提交、运行日志和部署状态；是否真正上线及正常运行，仍需检查对应部署与运行结果。[来源 S3]

## 2. 根据任务选择工具、模型与推理档位

### 2.1 优化目标

**在满足正确性、可靠性和实际能力要求的前提下，选择总完成成本合理、耗时可接受的组合。**

总完成成本应考虑实际计费的输入／输出与适用推理用量、工具费用、重试、返工、审查和等待时间。推理 token 若已计入某项输出费用，不重复计算。订阅场景还要考虑剩余额度、限流和机会成本，不能直接用 API 标价代替订阅消耗。

价格高不等于对当前任务一定更强；单价低也不等于完成整项工作更省钱。

### 2.2 先确认真实可用的能力

重要任务开始前，按需要确认：

| 项目 | 应确认的信息 |
| --- | --- |
| 开发工具／执行框架 | 文件编辑、终端、测试、浏览器、GitHub、多 Agent 等实际能力 |
| 模型 | 当前环境真实可选的精确标识、版本或快照 |
| 推理档位 | 模型与工具实际支持的档位，默认值及切换方式 |
| 上下文 | 当前实际可用窗口、使用量口径、压缩机制 |
| 成本与额度 | 计费方式、用户预算、限流和剩余额度（如可读取） |
| 权限与网络 | 能否读取项目、运行验证及访问必要服务 |

不能把界面存在一个名字当成模型已可用，也不能把其他工具支持的档位套用到当前环境。无法控制主模型时，应如实说明可控范围；有子 Agent 选择能力，也不代表可以切换主会话模型。

模型和工具应作为组合验证。Arena 对多个模型与工具组合的实验表明，在其测试范围内，同模型的实际成本会随工具配置变化；这支持联合评估，但不代表某个工具在所有项目中都更优。[来源 S4]

### 2.3 榜单的使用规则

**ModelDial 是优先参考的外部依据之一，并在外部榜单中给予较高权重。**

本次核实：用户提供的 `https://modeldial.com/radar` 跳转到 Coding 排名，页面快照为 2026-11-13。其方法论区分后端、前端、推理、审美和可维护性，默认展示模型的最高分配置；费用与耗时属于评测任务。[来源 S5、S6]

执行选型时：

1. 先按实际任务选择相关能力分项，再看综合排名。
2. 核对精确模型版本与推理档位，不把 max 的成绩当作 medium 的成绩。
3. 检查评测日期、任务范围、测试工具、费用口径和缺失数据。
4. 结合 Arena 中对应的 Agent、WebDev、文本或其他榜单做交叉检查。
5. 关注不确定性和样本局限，不因相邻名次或极小分差频繁换模型。
6. 最终以本项目的验收、错误情况、返工和总成本决定是否保留配置。

Arena 不同榜单的方法并不完全相同；WebDev 的网页结果比较和 Agent Arena 的真实任务评估不能混为一谈。[来源 S7、S8]

不把多个不同量纲的榜单分数直接求平均，也不声称一套未经验证的百分比权重具有科学最优性。建议采用：

**能力与权限门槛 → 本项目已有证据 → ModelDial 相关分项优先筛选 → 对应 Arena 榜单交叉检查 → 合格候选的总成本与耗时比较。**

对准备承担重要任务、但尚无项目记录的新组合，优先使用已有代表任务、现有验收条件或范围受限的试跑验证。不要求为每次小改动另建评测体系。

小任务复用已经验证的默认组合。新项目、重大阶段、现有组合明显退步、工具或模型发生重要变化时重新选型。可默认复用 14 天内的外部选型记录；这是资料复查偏好，不是要求每 14 天切换模型，也不是自动建立定时任务。

### 2.4 任务与模型角色

“高能力模型规划、经济型模型执行”是可用模式，是否采用由任务复杂度和风险决定。路由和任务分解已有公开实践，但没有依据要求所有规划一律使用最贵模型。[来源 S9、S10]

| 任务 | 默认选择方向 | 升级或验收重点 |
| --- | --- | --- |
| 文案修改、明确的小修复、机械性调整 | 已验证的快速经济组合；较低或适中推理 | 确认改动正确即可，不额外制造规划流程 |
| 需求边界、跨模块架构、复杂取舍 | 擅长推理与工程设计的高能力组合 | 明确假设、约束、接口、风险与验收 |
| 边界清楚的常规实现 | 可靠的经济或均衡组合；通常先用适中推理 | 按合同与行为验收，不只看是否编译 |
| 鉴权、权限隔离、金额计算、迁移、并发一致性 | 高能力组合参与关键设计与实现 | 失败场景、边界、数据安全和恢复 |
| 前端布局、交互与动画 | 优先匹配前端和视觉能力，并具备预览验证 | 复杂状态、动画时序、性能问题再提高能力或推理 |
| 根因不明、跨系统或反复失败的排障 | 能整合证据的高能力组合；提高推理视需要 | 先排除网络、权限和环境故障 |
| 关键审查与验收 | 能独立检查的合适组合 | 必须结合代码、测试和运行证据 |

模型角色可以由同一个模型承担。任务不复杂时，不必为“规划—执行—审查”的名称强制切换三次。

### 2.5 推理档位与升级条件

- 简单、确定且低风险的工作优先使用较低成本档位。
- 常规开发可从已验证的适中档位开始。
- 复杂架构、难定位缺陷、强约束推导及高错误代价任务，按需提高档位。
- 不要求所有任务使用最大推理。不同供应商的同名档位不能视为等价算力或等价成本。

以下情况触发重新评估：

1. 关键验收失败，当前方案的重要假设被推翻。
2. 默认经过两次有实质变化的修复尝试仍无新进展。
3. 任务暴露出更大的影响范围、数据风险或复杂依赖。
4. 预计重试和返工成本已超过升级的增量成本。

升级前先区分：信息不足、工具限制、环境故障、计划错误还是模型能力不足。随后选择补充证据、缩小任务、提高推理、切换模型或重做设计。网络不可用、凭证缺失或测试服务故障，不能靠机械换贵模型解决。

问题解决后，边界清晰的剩余工作可以回到经济组合。切换产生的重新加载、缓存变化和结果整合成本也应纳入考虑。

### 2.6 给执行 Agent 的任务合同

分派任务时应提供：

- 目标与完成条件。
- 必要背景、相关文件和源记录链接。
- 可修改范围与不能破坏的接口、行为、数据约束。
- 输入／输出、错误情况及必要验证。
- 与其他任务的依赖。
- 发现计划错误或实现超出范围时的反馈与调整方式。

执行 Agent 应基于证据修正问题，不能因为计划来自更强模型就盲目执行。重要调整同步回 GitHub。

重要任务的选型结论写入当前 Issue／PR 或现有选型文档。记录组合、选择原因、来源日期、实际结果和升级原因即可，不要求保存每次调用详情。

## 3. 上下文管理与约 50% 压缩偏好

### 3.1 正确理解成本和占用

需要区分四项指标：

- **当前上下文占用**：下一次模型处理时实际需要的工作内容。
- **模型／工具可用窗口**：当前配置允许的容量。
- **累计用量与费用**：整个会话已经消耗的输入、输出、重试和其他资源。
- **订阅额度**：产品自己的计量方式，不一定等于 token 数。

上下文常包含指令、工具说明、文件、消息和工具结果，不能只统计用户聊天字数。当前占用降下来，并不会退还已经产生的费用。

压缩可以减少后续需要携带的内容，但并非完全无损，也可能改变可复用的缓存前缀；应比较压缩开销、后续用量、信息损失和重新读取成本。[来源 S11、S12]

因此，50% 是 Alan 的保守工作偏好。没有充分依据把它表述为对所有模型、工具和任务都最省钱的统一阈值。

### 3.2 使用可核实的分母

优先使用工具公开的“当前活跃上下文／有效可用窗口”口径。若自行计算，应核实当前模型、运行模式、工具限制以及输出或推理预留；工具已经预留的部分不要重复扣除。

例如，确认有效窗口为 200,000 tokens 时，50% 对应约 100,000；有效窗口为 1,000,000 时，对应约 500,000。这只是比例换算，不是建议必须先积累到该数量。

百万窗口也应按需加载材料。为了保持一个百分比而保留大量无关历史没有收益。

看不到真实占用时，应标记“不可读取”或“估算”，根据阶段边界和工具原生机制管理；不能编造精确百分比。

### 3.3 默认触发规则

| 当前情况 | 默认动作 |
| --- | --- |
| 低于约 40%，内容仍与任务相关 | 正常工作，保持输出与读取范围精简 |
| 接近 40%–50% | 检查是否有过时材料，准备项目检查点 |
| 到达约 50% | 在最近的安全阶段边界完成检查点，并优先执行原生压缩 |
| 普通任务持续超过约 70% | 优先缩减工作集、拆分任务或压缩；解释继续保留长上下文的必要性 |
| 即将超过工具安全上限 | 遵守工具原生保护，不能为保留历史强行溢出 |
| 任务确实需要长上下文 | 可提高阈值，记录原因并保留足够执行余量 |

这些比例是可调整的触发偏好。一次工具结果可能让占用跃升，原生压缩也可能在 Agent 可写检查点之前发生；不能承诺每一刻都低于 50%。应持续更新项目状态，降低突然压缩造成的信息损失。

压缩后可把约 20%–35% 作为普通任务的期望区间，但不承诺固定压缩比。必要指令和当前材料已经超过这个区间时，缩小工作集或接受合理占用，不要反复压缩同一份内容。

### 3.4 压缩前保存什么

在可控的压缩前，更新当前项目记录，保留：

1. 当前目标和用户确认的决定。
2. 验收条件、约束和必要的授权边界。
3. 仓库、Issue、PR、分支及代码／验证基线。
4. 已完成与未完成事项。
5. 验证结果和关键证据路径。
6. 有价值的失败尝试及排除结论。
7. 未提交／未推送工作及同步情况。
8. 下一步可直接执行的动作。
9. 正在运行的任务或已有外部操作结果，避免恢复后重复执行。

保留结论与证据入口，不要求导出逐步思考过程。核心状态应进入 GitHub；无需为每次压缩新建一份 handoff 文件。

发生原生自动压缩而来不及更新时，恢复后先核对实际文件、分支、开放任务和已完成动作，再补齐记录。

### 3.5 优先减少无关内容进入上下文

- 先搜索路径、符号、错误片段，再读取相关范围。
- 大文件按章节、函数或区域读取；长日志先定位关键部分。
- 工具返回保留必要摘要与原始证据位置，避免反复载入相同完整输出。
- 稳定规则保持简短；详细背景按需检索。
- 可以独立开展的大量检索可交给子 Agent，返回结论、来源和必要片段。
- 对无关新任务使用新会话；相关任务压缩后继续，但按需重新读取权威记录。

压缩与切换后必须核对下一步和关键约束，不以摘要替代实际源文件的精确内容。

### 3.6 如何在工具中真正实现

**Markdown 规定行为，真实监测和自动压缩依赖运行工具提供的能力。**

按以下顺序实施：

1. 优先使用工具原生上下文统计、自动压缩阈值和手动压缩命令。
2. 若工具提供安全的事件接口，可在回合或工具调用边界读取占用并触发检查点；先验证统计口径及压缩能力。
3. 工具只允许用户执行压缩时，Agent 先保存状态，再给出该工具已核实的操作方式。
4. 没有可读取统计或可调用压缩接口时，采用阶段检查点、按需读取和原生自动压缩，说明限制。

不要把普通对话里写“已压缩”当成上下文实际减少；也不要用删除会话、清空所有历史替代必要状态保存。

#### Codex：已核实的配置示例

截至核实日期，官方配置参考列出：[来源 S13]

- `model_post_turn_compact_threshold_percent`：在最终回复后达到指定有效窗口百分比时压缩。
- `model_auto_compact_token_limit`：按 token 数触发自动历史压缩。

若当前安装版本支持，可以采用下面的回合结束设置：

```toml
model_post_turn_compact_threshold_percent = 50
```

这控制回合结束时的检查，不能保证单个很长执行回合的中途也一直低于 50%。如需回合内更早处理，需依据真实窗口设置适用的 token 阈值，并验证其生效方式。

工具或模型改变后要重新核对支持情况。不要通过虚报 `model_context_window` 来伪造阈值。Codex 也提供手动 `/compact`，但能否由当前 Agent 直接触发取决于所在产品界面。[来源 S14]

#### 自建 Agent 与其他工具

OpenAI Responses API 提供 `context_management` 的 `compact_threshold` 及独立 compact 接口，适合由开发者在支持的集成中实现；这不代表所有现成聊天应用都开放同样的控制。[来源 S11]

Claude Code 官方文档也说明原生自动压缩、`/compact` 和上下文查看机制；默认边界取决于模型和配置。[来源 S15]

其他工具（包括手机端或自建运行环境）应逐一核对其真实能力，不照搬其他产品的命令或参数。

### 3.7 日常长任务的适用边界

非开发任务同样可使用阶段记录、按需读取和约 50% 检查策略。记录放在该任务已授权的持久文档或工作系统中；私人生活内容不因本规范自动上传到代码仓库。

## 4. 多 Agent 协作

只有在子任务相互独立、边界清楚且预期收益超过额外成本时才并行。

- 每个 Agent 明确目标、输入、交付和文件范围。
- 对会写代码的并行任务，按需要使用独立分支、worktree 或清楚的文件归属。
- 共享文件和项目 STATUS 指定统一维护者，避免互相覆盖。
- 子 Agent 返回结果、改动位置、验证和未解决问题。
- 整合者检查接口、冲突和组合后的行为，维护最终 GitHub 状态。
- 并行增加的 token、工具、重试和整合成本要纳入总成本；低价模型的大量并发并不自动省钱。

## 5. 最终交付的简短格式

每次实质交付可按以下格式报告；不适用项可以省略：

```markdown
## 本次结果
- 完成内容：
- 验证结果及代码版本：
- GitHub 入口：Issue / PR / 分支
- 同步状态：本地提交 / 已推送 / 已合并
- 部署与线上验证：
- 剩余事项或阻塞：
- 下一步：
```

重要选型或上下文变化，补一句实际采用的组合、调整原因或当前限制即可，不持续刷屏报告普通操作。

## 附录 D：规则与配置的关系

| 层次 | 放在哪里 | 作用 |
| --- | --- | --- |
| 个人长期偏好 | 本文或个人维护的模板仓库 | 定义选择原则与工作目标 |
| 项目工作规则 | 项目内 AGENTS.md 与相关文档 | 把偏好结合项目限制落地 |
| 工具运行配置 | 当前工具实际支持的配置文件／设置 | 执行选模、推理、统计与自动压缩 |
| 当前任务状态 | GitHub Issue／PR／STATUS | 恢复正在进行的工作 |

如果未来用一个个人模板仓库管理多个项目，建议给模板标版本，各项目显式采纳更新；避免远程模板一改就无审查地改变所有项目规则。
